# Supabase changes, 13 Oct 2026

Four new migrations and one edge function update. No existing migration was edited.

## How to apply

1. Deploy the database first, then the function:
   ```
   supabase db push
   supabase functions deploy create-booking-request
   ```
2. If `db push` stops at `20261013170200_prevent_trainer_double_booking.sql`, read the
   `NOTICE` lines. Each one names a trainer and two overlapping active sessions.
   Cancel or move one session in each pair (Supabase dashboard), then run
   `supabase db push` again. Nothing from that migration is kept when it fails.
3. Test on staging first: book, double book the same slot (expect 409 SLOT_TAKEN),
   cancel more than 24h and less than 24h before, move more than 24h before.

Order matters: 170200 and 170300 use `public.session_time_range`, and the edge
function calls `public.check_trainer_slot`. Deploying the function before the
migrations makes every booking return 500.

## Migrations

### 20261013170000_add_session_price_snapshot.sql
- Adds `sessions.session_rate`, `sessions.service_fee`, `sessions.total_amount`
  (numeric(10,2), nullable, `if not exists`).
- Backfills rows with no snapshot. `booking_requests` has no amount columns, so the
  backfill uses the trainer price: `gym_price_per_session` when the session's
  `venue_choice` is `trainer_private_gym` and a gym price exists, else
  `price_per_session`. Fee is `round(rate * 0.05, 2)`, total is rate + fee.
- Adds `sessions_price_snapshot_nonnegative_check`.

Roll back:
```sql
alter table public.sessions drop constraint if exists sessions_price_snapshot_nonnegative_check;
alter table public.sessions
  drop column if exists session_rate,
  drop column if exists service_fee,
  drop column if exists total_amount;
```
(Roll back 170100 first, and the edge function too, because both use these columns.)

### 20261013170100_cancel_session_refund_from_snapshot.sql
- Replaces `cancel_session(p_session_id uuid, p_reason text default null) returns jsonb`.
  The signature and the returned keys stay the same.
- Refund is now based on `sessions.session_rate`, falling back to
  `trainers.price_per_session` only when the snapshot is null.
- 24h or more before start: refund = session_rate. Under 24h: refund = round(session_rate / 2, 2).
  The 5% fee is never refunded here. Trainer cancel or no-show has no path in the DB
  yet, so nothing changes there.

Roll back: re-run the `cancel_session` definition from
`20261012095559_firebase_identity_cutover.sql` (it reads `trainers.price_per_session`).

### 20261013170200_prevent_trainer_double_booking.sql
- `create extension if not exists btree_gist with schema extensions`.
- `public.session_time_range(timestamptz) returns tstzrange`, an IMMUTABLE helper for
  `[start, start + 1h)`. It is needed because `timestamptz + interval` is not immutable,
  so it cannot be used directly in a constraint.
- Guard DO block: if overlapping active sessions exist, it lists them as NOTICE lines
  and raises an exception, so the constraint is not created.
- `sessions_no_trainer_overlap`: `EXCLUDE USING gist (trainer_id WITH =,
  session_time_range(scheduled_at) WITH &&) WHERE (status IN ('confirmed','booked'))`.
  Those are the only active statuses in `sessions_status_check`. Cancelled, completed
  and reported sessions do not block a slot.
- `public.check_trainer_slot(p_trainer_id uuid, p_starts_at timestamptz,
  p_exclude_session_id uuid default null) returns text`. It returns 'ok', 'past',
  'not_offered' or 'taken', using the same rules as `get_trainer_booking_availability`
  (Dubai rolling 7 days, declared weekly start time, free). Only `service_role` can run it.

Roll back:
```sql
alter table public.sessions drop constraint if exists sessions_no_trainer_overlap;
drop function if exists public.check_trainer_slot(uuid, timestamptz, uuid);
-- Only after rolling back 170300 (it uses the helper):
drop function if exists public.session_time_range(timestamptz);
-- btree_gist can stay installed; it does no harm.
```

### 20261013170300_reschedule_safety.sql
- Replaces `get_reschedule_availability(p_session_id uuid) returns table(starts_at timestamptz)`
  and `reschedule_session_weekly(p_session_id uuid, p_new_scheduled_at timestamptz) returns void`.
  Their signatures stay the same.
- Both now raise `SESSION_NOT_MOVABLE` when the session is not confirmed or booked,
  or has already started.
- `reschedule_session_weekly`:
  - One move per booking stays in place (`SESSION_ALREADY_MOVED`).
  - A move under 24h before start raises the new `LATE_MOVE_PAYMENT_REQUIRED`. The
    "Pay to move" path goes through Tap later (TODO in the SQL). Moves 24h or more
    before start stay free.
  - If someone takes the slot between the check and the update, the exclusion
    constraint catches it and returns `SLOT_UNAVAILABLE`.
- `get_reschedule_availability` still returns slots when the session is under 24h
  away, so the app can show the Pay to move screen.

Roll back: re-run both definitions from `20261012095559_firebase_identity_cutover.sql`.

## Edge function: create-booking-request

The request body is unchanged. Changes for direct trainer bookings (`trainer_request`
with `scheduled_at`):

| Case | HTTP | Body |
|---|---|---|
| Success | 201 | see below |
| `scheduled_at` in the past or outside trainer availability | 400 | `{"error":"Validation failed","details":[...]}` |
| Client `session_rate` / `service_fee` / `total` differ from the server price | 409 | `{"error":"PRICE_CHANGED"}` |
| Slot already booked (pre-check, or exclusion constraint SQLSTATE 23P01) | 409 | `{"error":"SLOT_TAKEN"}` |
| DB raises `ACTIVE_CONCIERGE_EXISTS` (any request type) | 409 | `{"error":"ACTIVE_CONCIERGE_EXISTS"}` |

The session is written with the server's own `session_rate`, `service_fee` and
`total_amount`. Values sent by the client are only compared against them.

A 201 response keeps every existing key and adds four:
```json
{
  "success": true,
  "request_type": "trainer_request",
  "id": "<session id, or request id when no session>",
  "request_id": "<booking_requests.id>",
  "reference_code": "GSW-1234",
  "session_id": "<sessions.id>",
  "scheduled_at": "2026-10-14T03:00:00.000Z",
  "location_label": "...",
  "status": "confirmed",
  "session_rate": 250,
  "service_fee": 12.5,
  "total_amount": 262.5
}
```
`scheduled_at` is now always ISO 8601 UTC.

TODO(Tap): sessions are still inserted as `confirmed`. When Tap is connected,
insert them with a pending-payment status and let the Tap confirmation set `confirmed`
(marked in `insertConfirmedSession`).

Roll back: redeploy the previous `index.ts` from git.


## 20261013170400_append_concierge_note.sql

Adds `public.append_concierge_note(p_request_id uuid, p_note text)`, a security-definer
function that appends a customer's note to their own open Help me choose request
(Figma 3.6, "We added your new note to it"). It never changes status, trainer or
budget, only `booking_requests.message`, with a Dubai-time stamp. Execute is
granted to `authenticated` only.

Errors: `AUTH_REQUIRED`, `NOTE_REQUIRED`, `NOTE_TOO_LONG` (over 1,000 characters),
`OPEN_REQUEST_NOT_FOUND`.

Roll back: `drop function if exists public.append_concierge_note(uuid, text);`
The app treats a failure as "note not added" and simply hides the row, so rolling
back does not break sign-in.

## 20261013170500_anonymise_deleted_customer_records.sql

Makes the delete-account promise true: "your account, name, mobile number and email are
deleted within 30 days". The existing delete flow already removes the sign-in account,
profile, photo and notifications. This adds `public.anonymise_deleted_customer_records()`,
which, for every deletion whose profile cleanup has finished, strips the customer's name,
phone, email, messages and notes from retained `booking_requests` and `sessions` rows, and
removes home or outdoor addresses. Amounts, dates, statuses and trainer links stay, because
payment records must be kept. It runs daily at 02:15 Dubai time through pg_cron
(`getsetwell-anonymise-deleted-customers`) and records `records_anonymised_at`.

Roll back: `select cron.unschedule('getsetwell-anonymise-deleted-customers');`
then `drop function public.anonymise_deleted_customer_records();`. Already-anonymised
rows cannot be restored, which is the point.

## 20261013170600_remove_in_person_checks.sql

GetSetWell does not meet trainers in person. Deletes every `in_person` row from
`trainer_verification_checks` and replaces the `check_type` constraint so that value can
no longer be inserted. `seed.sql` no longer seeds "Met in person" rows.

Roll back: drop `trainer_verification_checks_check_type_check` and re-add it with
`'in_person'` in the list. The deleted rows are not restored.
